# LeagueMacroCoach — Project Checkpoint

Handoff summary for continuing development. Everything below reflects the state of the repo as of this checkpoint: a complete rule-based coaching pipeline — match retrieval through structured player insights, timeline enrichment, a deterministic item recommendation engine, a cross-pipeline coaching-session aggregator, and a benchmark-comparison foundation — plus one clearly-optional AI phrasing layer. **No part of the tool requires a paid API to function.** This supersedes the original checkpoint's "what's built" and "what's next" sections; those phases are complete and summarized below rather than repeated in full (see git history for the turn-by-turn build order).

**Strategic pivot (this checkpoint):** the project's primary goal is no longer AI coaching — it's a deterministic League intelligence system (live recommendations, drafting assistance, itemization, rune decisions, matchup analysis, a future overlay UI), with AI now formally an optional explanation layer project-wide, never the decision-maker. See the revised `ROADMAP.md` and new `RECOMMENDATION_SYSTEM_DESIGN.md`. Nothing already built changes meaning or behavior because of this pivot — it's additive, and the "AI never decides" rule it formalizes was already true for everything in this repo.

Player profile (`data/player_profile.json`): Riot ID `HelloKittler#meow`, NA, Mid, champion pool Yone/Akali/Fizz/Syndra. **20 real ranked games are in `data/database/game_history.json`**, all with timeline data enriched (deaths-before-objectives, objective-fight-presence are real numbers, not `"unavailable"`, for all 20).

## 1. What's built

**Rule-based macro pipeline (complete, exercised against real data):**
1. Riot API client — auth, PUUID lookup, match ID retrieval, match + timeline retrieval.
2. Multi-match importer/backfill — pulls N recent ranked matches, dedupes, runs each through the full pipeline (analysis → timeline → macro patterns → **item recommendations** → history), isolates per-match failures. `enrich_existing_timelines()` backfills timeline data onto matches imported before timeline support existed.
3. Structured analyzer — raw match → flat per-game stats.
4. Timeline analyzer — raw timeline → per-event derived facts (death timing vs. objectives, objective participation, fight participation). Only processes timeline *events*; does not parse per-minute `participantFrames` (see Limitations).
5. Macro pattern analyzer — threshold-based pattern flags, knowledge-aware de-prioritization, timeline-enriched when available.
6. Champion/role knowledge layer — hand-written markdown parsed into structured dicts.
7. History storage/aggregation — flat-JSON, upsert by match_id, cross-game trends and repeated-pattern detection.
8. Player profile + insight generation — `profile_summary.json` → `player_insights.json`, count-based confidence, honest `"insufficient_data"` handling.

**Deterministic item recommendation engine (complete, exercised against real data):**
9. `GameSnapshot` architecture (`src/analysis/game_state.py`) — source-agnostic shape, deliberately built so a future live-data builder can produce the same shape without touching anything downstream.
10. Item recommendation engine (`src/analysis/item_recommender.py`) — keyword-matched trigger evaluation against qualitative item knowledge, deterministic confidence scoring with a full breakdown, gold-aware `recommendation_type` (`complete_item`/`component`/`alternative`/`save_gold`), Data Dragon cross-check that flags (never silently drops or trusts) unrecognized item names. `generate_item_recommendations(match, game_name, tag_line, item_catalog, damage_type_table)` composes the full snapshot→knowledge→recommend pipeline into one callable — **now wired into `src/history/importer.py`'s `import_matches()`**, so item recommendations are generated automatically for every newly-imported match, not just via a separate manual step (see the architecture note below — this closed the exact gap the previous checkpoint flagged as a limitation).
11. Data Dragon static client (`src/riot/data_dragon.py`) — self-updates per patch automatically (see `PATCH_SYSTEM.md`).

**Optional AI phrasing layer (complete, never required):**
12. `src/ai/prompt_builder.py` / `validator.py` / `client.py` / `report_generator.py` — grounds a prompt in already-computed insights + knowledge, strips any model output not traceable to real data, opt-in Anthropic backend. The tool works fully without this layer; `ROADMAP.md` still recommends a free deterministic backend as the actual default (not yet built — see Next Milestone).

**Coaching-session aggregation layer (complete, exercised against real data):**
13. `src/coaching/coaching_report.py` — combines `player_insights.json`, one match's macro patterns + item recommendations, and (if present) a benchmark comparison into one `coaching_session.json`. Pure combination, no new analysis.
14. `src/coaching/priorities.py` — selects top 1–3 lessons, preferring cross-game recurring patterns over this-game-only observations, explicitly labeled by evidence `scope`.
15. `src/coaching/formatter.py` — pure terminal rendering, no decision-making.

**Benchmark comparison foundation (complete, zero real data by design):**
16. `src/benchmark/benchmark_schema.py` — benchmark entry shape + `METRIC_DIRECTIONS` registry (direction-aware: higher-is-better vs. lower-is-better).
17. `src/benchmark/storage.py` — flat-JSON load/save/upsert, mirroring `history/store.py`'s pattern; `find_benchmarks()` supports arbitrary extra descriptor filters (e.g. a future `matchup` field) with no code changes needed later.
18. `src/benchmark/comparison.py` — direction-aware gap-ratio severity scoring, verified against a hand-worked example before trusting the formula.
19. `src/coaching/benchmark_section.py` — wires stored benchmarks into `coaching_session.json` as a strictly informational section. **Benchmark gaps never become coaching priorities** — verified by a test that builds the same session with and without benchmark data present and asserts `main_lessons`/`next_game_focus` are identical either way.
20. **No real benchmark data exists anywhere in the repo.** `data/benchmarks/` isn't even created yet. No scraping, no AI-sourced numbers — this is 100% foundation, verified only with synthetic test fixtures.

**Architecture/planning documentation (complete):**
21. `ROADMAP.md`, `ARCHITECTURE_AUDIT.md`, `TEST_AUDIT.md`, `KNOWLEDGE_SYSTEM_PLAN.md`, `LIVE_SYSTEM_DESIGN.md`, `UI_DESIGN.md`, `PATCH_SYSTEM.md` — a full engineering review and forward design pass covering everything not yet built (live game state, overlay UI, knowledge scaling, patch handling). `ROADMAP.md` was revised this checkpoint for the deterministic-intelligence-system pivot (below); `RECOMMENDATION_SYSTEM_DESIGN.md` is new.

**Shared recommendation contract (foundation only, no migration yet):**
22. `src/recommendations/schema.py` — the shared shape every future recommendation-producing system (item, draft, rune, live, macro) will eventually emit: `system`/`category`/`subject`/`recommendation`/`reason`/`evidence`/`confidence`/`confidence_score`/`severity`/`priority`/`source`/`details`. Two deliberately separate axes — `confidence` (data quality) and `severity` (impact/urgency) — replace the three previously-incompatible confidence vocabularies `ARCHITECTURE_AUDIT.md` Finding C flagged. `validate_recommendation(entry) -> list[str]` follows the exact convention `benchmark_schema.py`'s `validate_benchmark_entry()` already established. **`recommendation`/`confidence_score` may be `null`, and `confidence`/`severity` may be `"unavailable"` — this is a valid, expected state, never rejected.** `details` stays permissive of arbitrary domain-specific keys, same precedent as benchmark entries.
23. `src/recommendations/adapters.py`: `adapt_item_recommendation(entry)` and `adapt_macro_lesson(lesson)` translate one entry from `item_recommender.recommend_items()`'s output / one lesson from `priorities.select_priorities()`'s output into the shared schema. **Neither source module is imported, called, or modified** — the adapters are hand-written pure functions operating on plain dicts matching those modules' real shapes; `item_recommender.py` and `coaching/priorities.py` are byte-for-byte unchanged. Both adapters reuse each source's single confidence value for the schema's `severity` field too, since neither source system computes impact/urgency independently yet — an explicitly-documented simplification, not a hidden decision.
24. **The Stage-1 adapters are now wired into `src/coaching/coaching_report.py`.** `build_coaching_session()` calls a new private helper, `_shared_recommendations(item_recommendations, main_lessons)`, which runs every item recommendation through `adapt_item_recommendation()` and every selected macro lesson through `adapt_macro_lesson()`, and adds the combined list as a new `"shared_recommendations"` key on the returned session dict — purely additive, alongside `main_lessons`/`item_review`, never replacing either. `coaching_session.json` now carries this extra key; every existing key (`player`, `champion`, `game_result`, `main_lessons`, `item_review`, `benchmark`, `strengths`, `next_game_focus`) is unchanged in shape or value. `_shared_recommendations()` contains no translation logic of its own — it only calls the two existing adapters and concatenates their output, keeping the "modules perform logic, orchestrators only coordinate" rule intact. When item recommendations are unavailable for a match, `shared_recommendations` simply contains macro-only entries rather than failing — same honest-degradation behavior as `item_review`'s existing `"unavailable"` path. `src/coaching/formatter.py` was not touched; it renders known keys via `.get()` and silently ignores the new one, so terminal output is byte-for-byte unchanged.

**Shared polling/runtime foundation (foundation only):**
25. `src/runtime/poller.py` — `SessionPoller`, the shared runtime `ROADMAP.md` §1 and `LIVE_SYSTEM_DESIGN.md`'s "Runtime Model" section both call the actual prerequisite for `src/draft/`/`src/live/`. Deliberately domain-blind: it has zero knowledge of champ select, live games, draft, runes, or any analysis — it only calls an injected zero-argument `data_source()` callable (returns a dict when a session exists, `None` when it doesn't — the same "endpoint simply isn't reachable" idle condition `LIVE_SYSTEM_DESIGN.md` documents for the Live Client Data API), tracks `state` (`"idle"`/`"active"`) off the last result, and hands each result to an optional `on_result` callback. `poll_once()` is the single synchronous unit everything else is built from — it's also the integration point a future desktop app can call directly from its own timer/event loop instead of using this module's background thread at all. `start()`/`stop()` run/stop that same `poll_once()` on a background `threading.Thread` at a configurable `interval_seconds`, with an injectable `sleep_fn` (defaults to `time.sleep`) so tests never depend on real wall-clock waits longer than tens of milliseconds. Both `start()` and `stop()` are idempotent. No draft/rune/live analysis logic, no UI, nothing League-specific lives here.

**`src/draft/` foundation — data access only, no recommendation logic:**
26. `src/draft/client.py` — `LCUClient`, the League Client Update API client. Reads the per-launch lockfile (`name:pid:port:password:protocol`, one line, colon-separated — the League client's own documented mechanism, not reverse-engineered traffic), builds HTTP Basic auth from it (`build_auth()`, fixed username `"riot"`), and makes an authenticated `GET` to `https://127.0.0.1:{port}/lol-champ-select/v1/session` over a self-signed cert (`verify=False`). Returns the raw response dict on success, and `None` for every honestly-expected "nothing to report" case — no lockfile (League client not running), a `404` (client open, no champ-select session right now), or a connection error (client closed mid-poll) — matching the "unavailable, never fabricated" discipline already established project-wide. An unexpected server error (anything but 404) still raises rather than being silently swallowed as `None`, since masking a real bug as an absence would violate that same discipline in the other direction. `LCUClient` instances are directly callable (`__call__` → `get_champ_select_session()`), so an instance can be passed straight into `SessionPoller(data_source=...)` with no wrapper — verified by tests that build a real `SessionPoller` around a fake-lockfile-backed `LCUClient` and confirm `state` flips `"idle"`/`"active"` correctly. `parse_lockfile()`/`build_auth()`/`get_champ_select_session()`'s HTTP call are each independently unit-tested; `LCUClient`'s constructor takes an injectable `get_fn` (defaults to `requests.get`), mirroring `src/riot/data_dragon.py`'s existing `get_fn`-injection precedent rather than introducing a new mocking approach. No real League installation is touched anywhere in the test suite — lockfiles are temp files the tests write themselves, and every HTTP call goes through a fake `get_fn`.
27. `src/draft/snapshot.py` — `build_draft_snapshot(raw_session)`, converting a raw `/lol-champ-select/v1/session` dict (the shape `LCUClient` returns) into a source-agnostic `DraftSnapshot` plain dict. Same role for the draft phase that `GameSnapshot`/`build_snapshot_from_match()` (`src/analysis/game_state.py`) plays for post-game data: this is the only file that knows the LCU's specific field names (`myTeam`/`theirTeam`/`cellId`/`championId`/`assignedPosition`/`timer.phase`/...) — any future pick/ban recommendation engine reads only the resulting plain dict. Extracts `ally_team`/`enemy_team` (full 5-slot rosters — `cell_id`, `champion_id`, `assigned_position`), `ally_picks`/`enemy_picks` (flat lists of locked-in champion IDs, derived from those rosters), `ally_bans`/`enemy_bans` (from `bans.myTeamBans`/`bans.theirTeamBans`), `current_player` (the `ally_team` entry matching `localPlayerCellId`, or `None` if unmatched), and `phase` (normalized from `timer`: `name`/`time_left_ms`/`is_infinite`). The LCU's own `championId: 0` convention for "not picked yet" is normalized to `None`, and a blank `assignedPosition` (privacy/blind-pick) also normalizes to `None` — same "never invent data" discipline `game_state.py` already follows. `build_draft_snapshot(None)` and `build_draft_snapshot({})` both return `None` — no session means no snapshot, mirroring `SessionPoller`'s own idle convention, never a fabricated empty-but-present snapshot. **No pick/ban recommendation, synergy, counter, or rune logic exists here or anywhere yet** — structured extraction only, per explicit instruction this checkpoint.

**Champion knowledge foundation for draft/matchup/rune/item recommendations (new this checkpoint, data format + loader + validation only, no recommendation logic):**
28. `src/knowledge/champion_schema.py` — `REQUIRED_FIELDS`/`VALID_ROLES`/`VALID_DAMAGE_TYPES`/`VALID_SCALING_PROFILES` and `validate_champion_profile(entry) -> list[str]`, the shared shape every future draft recommendation, matchup analysis, rune recommendation, and item recommendation system will read from (`champion`, `roles`, `damage_type`, `scaling_profile`, `strengths`, `weaknesses`, `preferred_playstyle`, `common_counters`, `favorable_matchups`, `synergy_champions`). Same "returns error strings, never raises" convention already established twice in this codebase (`benchmark_schema.py`'s `validate_benchmark_entry()`, `recommendations/schema.py`'s `validate_recommendation()`). `VALID_ROLES` reuses Riot's own `teamPosition` vocabulary (`top`/`jungle`/`middle`/`bottom`/`utility`) already used by `game_state.py`/`loader.py`, and `VALID_DAMAGE_TYPES` reuses `data/static/champion_damage_types.json`'s existing vocabulary (`physical`/`magic`/`hybrid`/`unknown`) — no new naming scheme invented where a compatible one already existed. `"unknown"` is the honest-absence value for `damage_type`/`scaling_profile`, `[]` for every list field, `None` for `preferred_playstyle` — all explicitly valid, never rejected.
29. `src/knowledge/champion_loader.py` — `load_champion_profile(champion, champions_dir=...)`, parsing `knowledge/champions/{champion}_profile.md` into a dict matching `champion_schema.py`'s shape, then validating it before returning. **Deliberately a sibling to `src/knowledge/loader.py` and `src/knowledge/item_loader.py`, not an extension of either** — same "different-enough shape, own loader" precedent `item_loader.py` already established relative to `loader.py`. Uses a distinctly-named file per champion (`{champion}_profile.md`, not `{champion}.md`) specifically so this new draft-knowledge record type can coexist in the same `knowledge/champions/` directory as the pre-existing, unrelated `{champion}.md` macro-coaching files (`Expected Role`/`Important Metrics`/`Common Mistakes to Detect`/...) **without touching them at all** — `loader.py`'s `load_champion()` and everything that calls it (`macro_analyzer.py`) is completely unaffected; the two record types are parsed by two independent functions reading two independently-named files. A missing profile file returns `None` (honest absence, matching `load_champion()`'s existing convention); a malformed *existing* file raises `ValueError` instead — a hand-authored file failing validation is a real authoring bug, not an expected absence, mirroring the "missing lockfile → `None`, malformed lockfile → raises" split `src/draft/client.py` already established this checkpoint sequence. The champion's canonical name is read from the file's own `# Heading` (matching the existing `# Yone`-style H1 convention already used in every other knowledge file), falling back to the caller's argument only if no heading is present.
30. **Five real profile files authored** for the player's existing champion pool — `knowledge/champions/{yone,akali,fizz,syndra,pyke}_profile.md` — matching `champion_damage_types.json`'s existing damage-type classifications for consistency (Yone hybrid, Akali/Fizz/Syndra magic, Pyke physical) and each hand-written with real, accurate League knowledge (roles, scaling, strengths/weaknesses, common counters, favorable matchups, synergy champions). Same tier-1 "player's own pool first" priority `KNOWLEDGE_SYSTEM_PLAN.md` already established for the coaching and item knowledge files.

**Champion-ID catalog + first deterministic draft recommender (new this checkpoint):**
31. `src/riot/data_dragon.py` gained a champion catalog, additive to the existing item catalog with zero shared mutable state: `fetch_champion_data()`/`build_champion_catalog()`/`load_champion_catalog()` mirror `fetch_item_data()`/`build_item_catalog()`/`load_item_catalog()` exactly (same `fetch_latest_version()` call, same `STATIC_DIR`, own cache filename `champion_data_{version}.json` so the two caches never collide), and `champion_name_from_id(catalog, id)`/`champion_id_from_name(catalog, name)` are the two never-guess lookup functions `DraftSnapshot` needed to connect its champion **IDs** to `champion_schema.py`'s champion **names** — the exact gap the prior checkpoint's limitations section flagged. The catalog keys off Data Dragon's `"key"` (numeric id) and `"name"` (display name) fields specifically, never the outer dict key or `"id"` field, both of which are an internal slug (e.g. `"MonkeyKing"` for the champion actually named `"Wukong"`) — a real edge case, covered explicitly by a test. Both new lookup functions return `None` for an unrecognized id/name, never a guess. No existing item-catalog function, cache file, or test was touched.
32. `src/draft/recommender.py` — `recommend_draft(snapshot, champion_catalog, profile_loader_fn=load_champion_profile, candidate_names=None) -> list[dict]`, the real recommendation logic that reads a `DraftSnapshot`. **Dispatches on whether `current_player.champion_id` is locked in**, to two genuinely different behaviors that must not be conflated:

    - **Locked-champion informational callouts** (`current_player.champion_id` is set) — `_recommend_for_locked_champion()`, unchanged since this module's first version (see item 33 below for what changed and what didn't). Only surfaces facts the current player's *own* champion profile already states about itself — an enemy pick that's one of `common_counters` (`category: "counter_warning"`, `severity: "high"`), an enemy pick that's a `favorable_matchups` entry (`category: "favorable_matchup"`, `severity: "low"`), or an ally pick that's a `synergy_champions` entry (`category: "ally_synergy"`, `severity: "medium"`). `recommendation` stays `null` on every entry here — these are warnings/callouts, not "do this" instructions.
    - **Pre-lock pick recommendations** (`current_player.champion_id` is `None`) — `_recommend_champion_picks()`, new this checkpoint (item 33 below). Recommends *which* champion to consider next, natively in the shared schema, `category: "pick_recommendation"`.

    Both paths resolve champion **ids** to names via `champion_name_from_id()` (never fabricating a name for an id the catalog doesn't recognize), emit **natively** in `src/recommendations/schema.py`'s shared shape (no adapter, since draft has no legacy shape to preserve, per `RECOMMENDATION_SYSTEM_DESIGN.md` §4), and validate every entry with `validate_recommendation()` before returning — an invalid entry would be a bug in this module, so it raises rather than degrading silently, the same discipline `champion_loader.py` already applies to its own output. `_finalize()` (assign `priority` 1..n, validate) is the one piece of logic genuinely shared between both paths.
33. **Pre-lock pick recommendations (`_recommend_champion_picks()`, new this checkpoint) — correcting a real gap in the prior checkpoint.** The prior checkpoint's `recommend_draft()` only ever returned `[]` when no champion was locked in yet — true for most of a real champ-select session — so it never actually delivered the "recommend a champion" milestone `ROADMAP.md`/`RECOMMENDATION_SYSTEM_DESIGN.md` describe for the draft system, only the narrower "comment on an already-made pick" behavior. This checkpoint fills that gap without touching the locked-champion path at all (verified: every pre-existing `test_draft_recommender.py` test still passes unmodified, except one that was testing the *old* `[] `-for-everything placeholder behavior for the unlocked case specifically — see the architectural decision below on why that one test's expectations changed).

    **Candidate discovery:** `candidate_names` is injectable (for tests); when `None`, defaults to `src/knowledge/champion_loader.py`'s new `list_available_champion_profiles()`, which discovers every `knowledge/champions/{champion}_profile.md` on disk and returns their canonical names, sorted deterministically — never a hardcoded roster, never inventing a profile that doesn't exist.

    **Filtering (both required, not scored):** a candidate must (1) have an authored profile (`profile_loader_fn(name)` returns non-`None`) and (2) list the current player's `assigned_position` in its `roles` — role fit is a hard filter per explicit instruction, not a scoring bonus. Every champion already appearing in `ally_picks`, `enemy_picks`, `ally_bans`, or `enemy_bans` (resolved via the catalog) is excluded before scoring.

    **Scoring — small, named, fully inspectable, authored-facts-only (no win rates, no scraped stats, no AI, no hidden weights, no counter matrices):**
    - `damage_balance` (`DAMAGE_BALANCE_BONUS = 2`): counts locked allies' `damage_type`s (`physical`/`magic`/`hybrid`; `"unknown"` and allies with no authored profile contribute to nothing). Below `MIN_LOCKED_ALLIES_FOR_DAMAGE_SIGNAL = 2` known-damage-type allies, or when `physical`/`magic` counts are tied, `_damage_balance_need()` returns `None` — genuinely insufficient data or a balanced comp, never a fabricated "need." Otherwise a `physical`-heavy team favors a `magic` candidate, and a `magic`-heavy team favors a `physical` **or** `hybrid` candidate (hybrid counts as a valid diversifying answer to a magic-heavy comp, per explicit instruction).
    - `direct_synergy` (`DIRECT_SYNERGY_BONUS = 1`): awarded once (flat, not scaled per match) when the candidate's own `synergy_champions` list explicitly names a locked ally — never inferred from the ally's profile, only the candidate's.
    - `strengths`/`preferred_playstyle` are copied into `details` for transparency but **never scored** — a longer `strengths` list earns nothing, per explicit instruction; a dedicated test (`test_pick_recommendation_details_include_strengths_and_playstyle_without_scoring_them`) proves this.
    - `details.score_breakdown` is always `{"role_fit": "required", "damage_balance": <int>, "direct_synergy": <int>, "total": <int>}` — every entry's score is fully re-derivable from its own `details`, nothing hidden.

    **Ranking:** total score descending, then canonical champion name ascending as a deterministic tie-break (verified by a dedicated test with three same-scoring candidates). Truncated to the top `TOP_N_PICK_RECOMMENDATIONS = 3` after sorting — full candidate evaluation still happens, only the returned list is capped.

    **Honest degradation, each with a dedicated test:** no `assigned_position` known → one `_unavailable_pick_entry()` (`confidence`/`severity: "unavailable"`, `recommendation: null`, `subject: "role_unavailable"`), never fabricated role advice. Zero eligible candidates after filtering → one `_unavailable_pick_entry()` (`subject: "no_eligible_candidates"`). Every ally pick id the catalog can't resolve is listed in every returned entry's `details.unresolved_ally_ids`; every resolved ally name with no authored profile is listed in `details.missing_ally_profiles` — both computed once per call, never silently dropped. Nothing in either new function mutates its `snapshot`/`champion_catalog`/profile inputs (verified by a `copy.deepcopy`-before/after equality test).

**Conservative enemy-side pick-recommendation signals (new this session — Stage 1 of a staged implementation plan; see items 35–37 below for Stages 2–3, and Sec.4 for what's still ahead):**
34. `_recommend_champion_picks()`'s scoring gained two more signals, both reading **only the candidate's own profile** against currently locked enemy picks — never the enemy's own profile, and never an inferred/reversed relationship (a locked enemy whose own profile happens to list the candidate is irrelevant; only what the candidate's profile says about that enemy matters). This is the same "candidate's own authored facts only" discipline `damage_balance`/`direct_synergy` already established, extended to the enemy side:
    - `favorable_enemy_matchup` (`FAVORABLE_ENEMY_MATCHUP_BONUS = 1`): awarded once (flat, same "not scaled per match" rule as `direct_synergy`) when the candidate's own `favorable_matchups` list explicitly names one or more currently locked enemy picks.
    - `common_counter_risk` (`COMMON_COUNTER_RISK_PENALTY = 1`): awarded (as a positive risk magnitude, then *subtracted* from `total`) once when the candidate's own `common_counters` list explicitly names one or more currently locked enemy picks — i.e., the candidate would be walking into a pick that's a known threat to them.
    - `details.score_breakdown` is now `{"role_fit": "required", "damage_balance": <int>, "direct_synergy": <int>, "favorable_enemy_matchup": <int>, "common_counter_risk": <int>, "total": <int>}`, where `total = damage_balance + direct_synergy + favorable_enemy_matchup - common_counter_risk` — every component still individually inspectable, nothing hidden. Severity thresholds on `total` are unchanged from before this stage (not touched, per "preserve all existing behavior").
    - `details` also gained `unresolved_enemy_ids` (locked enemy pick ids the catalog couldn't resolve — mirrors the existing `unresolved_ally_ids`) and `locked_enemy_names` (the full deduplicated list of currently locked enemy names actually used for this computation, present on every entry regardless of whether either signal fired, for full auditability). Locked enemy picks are deduplicated by name (`list(dict.fromkeys(...))`) before scoring — a repeated/duplicate enemy id can never double-count a bonus or penalty.
    - **Missing enemy profiles never matter.** Neither new signal ever calls `profile_loader_fn` on an enemy — only the candidate's already-loaded profile is read — so an enemy with no authored profile at all still fully participates in both signals, verified by a dedicated test.
    - The locked-champion path (`counter_warning`/`favorable_matchup`/`ally_synergy`), role filtering, pick/ban exclusion, damage-balance scoring, direct-synergy scoring, the top-3 cap, and the deterministic alphabetical tie-break are all **completely untouched** — every pre-existing `test_draft_recommender.py` test required zero changes; only the shared test helper `_make_catalog_and_profiles()` gained two new optional spec keys (`common_counters`/`favorable_matchups`, previously hardcoded to `[]`) and one existing mutation test's fixture was widened (not behaviorally changed) to also exercise a locked enemy pick.

**End-to-end draft runtime orchestration (new this session — Stage 2):**
35. `src/draft/client.py`'s `LCUClient` gained one small, purely additive method: `is_client_running() -> bool`, a cheap local-only check (does the lockfile exist — no network call) for whether the League *client* itself is open, independent of whether a champ-select session exists. `get_champ_select_session()` — unchanged, still collapses "client not running" and "client open but no session" into the same `None`, per the earlier checkpoint's deliberate design decision — was **not** touched or reinterpreted; this is a new capability sitting alongside it, not a reinterpretation of existing behavior. Exists specifically because `DraftRuntimeService` (below) needs to distinguish those two states and the existing method's contract couldn't provide that without changing it.
36. `src/draft/service.py` — `DraftRuntimeService`, the first module to actually wire the whole draft chain together: an injected `session_source` (LCUClient-shaped) → `snapshot_builder` (defaults to `build_draft_snapshot`) → `champion_catalog_loader` (defaults to `load_champion_catalog`) → `recommender` (defaults to `recommend_draft`) → one plain application-state dict via the synchronous `poll_once()`. Every dependency is injected; `session_source`/`client_running_check` have no default (mirroring `SessionPoller`'s own `data_source`-required precedent — no default would exist that doesn't silently touch a real LCU connection), while the three pure/already-safe-to-default dependencies keep the same real-function defaults `recommend_draft()` already established for `profile_loader_fn`. Distinguishes four states: `league_client_unavailable` (client not running — `client_running_check()` short-circuits before `session_source()` is even called), `idle_no_champ_select` (client running, no session, or `snapshot_builder` honestly returns `None`), `champ_select_active` (a real snapshot was built and run through the recommender — covers **both** locked and pre-lock sub-cases, since `recommend_draft()` itself already dispatches on that), and `processing_error` (any unexpected exception from any step). Every external call (`client_running_check`, `session_source`, `snapshot_builder`, the champion-catalog load, `recommender`) is individually wrapped in its own `try`/`except`, so one failing step degrades to `processing_error` for *that* poll only — nothing is cached or flagged permanently broken, and the very next `poll_once()` call retries every step from scratch (verified by a dedicated test: a `session_source` that fails once then succeeds recovers cleanly on the second poll). The champion catalog is the one deliberate exception to "never cache anything": it's loaded lazily on first use and cached **only after a successful load**, so a real catalog fetch isn't repeated every poll once it succeeds, but a transient failure is still retried next poll rather than being silently abandoned forever. `poll_once()` is directly usable as `SessionPoller(data_source=service.poll_once)` — it satisfies the exact same "zero-arg callable returning `dict | None`" contract `SessionPoller` already requires (it happens to always return a `dict`, never `None`, which is a valid degenerate case of that type, verified by a dedicated compatibility test). Never includes lockfile passwords, auth headers, or any other credential — structurally guaranteed, not merely policy, since this module never touches `LCUClient` internals at all, only the plain return values of its injected callables (verified by a test that serializes every state dict to JSON and checks for credential-shaped substrings). `warnings` is a reserved-but-currently-always-empty list field, kept honest rather than fabricated. `state_schema_version` (currently `1`) is included on every returned dict for a future consumer (Stage 3's publisher, eventually a UI) to detect a shape change.

**Atomic local state publisher (new this session — Stage 3):**
37. `src/runtime/state_publisher.py` — `publish_state(state, output_path=DEFAULT_OUTPUT_PATH)`, the local output layer a future desktop UI (not built) will read. Validates `state`'s basic shape via `validate_state_shape()` (the same seven top-level keys `DraftRuntimeService.poll_once()` always returns — same "returns error strings, doesn't raise" convention `validate_recommendation()`/`validate_champion_profile()` already established), raising `InvalidStateError` for a missing key — a real upstream bug, not an expected absence. Serializes to deterministic JSON (`indent=2, sort_keys=True`) **before** touching the filesystem at all, so an unserializable value raises `TypeError` with zero filesystem side effects. Writes atomically: a temp file in the *same directory* as the target (via `tempfile.mkstemp`), then `os.replace()` — atomic on both POSIX and Windows since Python 3.3, so a reader can never observe a partially-written file. Creates the target's parent directory if missing. On any failure before the swap, the temp file is removed and the real output path is left completely untouched (verified by a test that forces `os.replace()` to fail — by pointing `output_path` at an existing directory — and confirms no stray temp file survives). Default target: `reports/runtime/draft_state.json`. Contains no recommendation logic and makes no League API calls of any kind — it only ever takes an already-computed dict and writes it.

**Runnable draft CLI (new this session — Stage 4; first real, usable-today consumer of the whole chain):**
38. `src/draft/cli.py` — `python -m src.draft.cli --once` / `--watch`, following the exact "`argparse` in `main()`, plain injectable functions underneath" shape `src/history/backfill.py` already established. `--once` performs a single `DraftRuntimeService.poll_once()`, publishes it via `publish_state()`, prints a concise status line, and exits. `--watch` drives `poll_once()` in a plain `while True: poll -> publish -> print -> sleep` loop with an injectable `sleep_fn`, catching `KeyboardInterrupt` around the whole loop to shut down cleanly on Ctrl+C — **deliberately not** `SessionPoller.start()`'s background thread: this CLI's entire job while running *is* to watch, so there's no second thread of work the main thread needs to stay free for (unlike a future UI, which is exactly why `SessionPoller`'s threaded design exists). This still reuses `poll_once()` as its foundation rather than reimplementing polling logic — the loop body is the same trivial "call it, sleep, repeat" shape `SessionPoller._run_loop()` itself uses internally, not a second retry/backoff/idle-tracking implementation. `--output PATH` (default `reports/runtime/draft_state.json`), `--interval SECONDS` (default `5.0`, `--watch` only), `--lockfile PATH` (default: `LCUClient`'s own standard-install default), and `--verbose` (also print the full JSON state) round out the options. `--once`/`--watch`/`--capture-once` (item 39 below) are a `required=True` mutually-exclusive `argparse` group — exactly one must be given. Manually smoke-tested end to end on this machine (no League installed): `--once` correctly reports `league_client_unavailable` and writes a real, valid `reports/runtime/draft_state.json`. `reports/runtime/` added to `.gitignore` (mirroring the existing `reports/generated_reports/` pattern) since this is generated, regenerable output, never authored content.

**Sanitized champ-select capture tool (new this session — Stage 5):**
39. `src/draft/capture.py` — `sanitize(value)` and `capture_champ_select(raw_session, snapshot, capture_dir=DEFAULT_CAPTURE_DIR, clock_fn=...)`, wired into the CLI as `python -m src.draft.cli --capture-once`. Exists to close a gap flagged repeatedly across this checkpoint's history: every LCU/`DraftSnapshot` fixture in this codebase is hand-built from Riot's public documentation, never verified against a real running client. `sanitize()` recursively redacts a small, **named-by-key** (not path-specific) set of sensitive field names — `password`, `chatRoomPassword`, `puuid`, `summonerId`, `accountId`, `displayName`, `gameName`, `internalName`, `riotId`, `tagLine`, `authorization`, `token`, `secret` (case-insensitive match) — wherever they appear at any nesting depth, replacing each value with a fixed `"[REDACTED]"` placeholder rather than deleting the key, so field *names* and structure stay intact for a byte-for-byte comparison against this project's hand-built fixtures. Name-based rather than path-based specifically because the real response shape isn't confirmed yet — a path-specific sanitizer could miss a sensitive field sitting somewhere this project didn't anticipate. `capture_champ_select()` writes two sanitized files per capture (a raw-session sample and the normalized `DraftSnapshot` — the latter already structurally safe by construction, since `build_draft_snapshot()`'s narrow allowlist-style extraction never touches `puuid`/`summonerId` in the first place, but sanitized anyway for consistency), each carrying a fixed, human-readable review-before-sharing warning baked into the file itself (`CAPTURE_FILE_WARNING`), not just left as external documentation. Filenames are timestamp-based via an injectable `clock_fn`, deterministic in tests. Default output: `reports/captures/` — deliberately separate from both `tests/` (authored fixtures) and `reports/runtime/` (the regular published app state), and added to `.gitignore` the same way. `run_capture_once()` (`src/draft/cli.py`) is the only caller, itself only reachable via the explicit `--capture-once` flag — never invoked from `run_once()`/`run_watch()`, never automatic. Writes nothing at all (no directory even created) when no champ-select session is active, verified by a dedicated test and by a real manual smoke test on this machine. Every test uses fake session payloads only — no real LCU client, no real League installation.

**Desktop application foundation (new session — Stage 1 of a 10-stage plan building the first local desktop app; see Sec.4 for what's still ahead):**
40. `src/ui/state_reader.py` — `read_runtime_state(path=DEFAULT_STATE_PATH) -> StateReadResult`, the UI-independent reader for the JSON file `publish_state()` writes. `StateReadResult` is a frozen dataclass (`status`, `state`, `source_path`, `modified_at`, `error`) with five statuses as module-level string constants (`file_missing`/`valid_state`/`invalid_json`/`invalid_state_shape`/`read_error`), mirroring `DraftRuntimeService`'s own string-constant-for-state convention rather than introducing a new `enum.Enum` pattern nothing else in this codebase uses. **Reuses `state_publisher.py`'s own `validate_state_shape()` for the shape check** rather than re-deriving a second copy of the same required-fields list — reader and writer share exactly one definition of "valid," so they can never silently drift apart. `DEFAULT_STATE_PATH` is a direct alias of `state_publisher.DEFAULT_OUTPUT_PATH` (same reuse discipline, verified by a dedicated test). Every honestly-expected failure mode returns a result instead of raising — including a top-level `except Exception` catch-all for any genuinely unexpected OS-level read failure, reported only as `{ExceptionClassName} while reading {filename}`, deliberately never the exception's own message or a traceback (a filesystem exception message could itself contain the full absolute path or other environment detail not appropriate to surface in a UI). Extra, forward-compatible top-level fields in the JSON are never stripped — the reader returns the parsed dict as-is once shape validation passes, so a future `DraftRuntimeService` field addition doesn't require a reader change to keep working. No UI code, no League API logic, no recommendation logic — structured file I/O only.
41. `src/ui/state_watcher.py` — `StateWatcher`, built on `SessionPoller` **by composition, not duplication**: internally owns a `SessionPoller(data_source=self._read, on_result=self._handle_result, sleep_fn=...)`, so `start()`/`stop()`/`poll_once()`/`is_running` all delegate straight through, reusing SessionPoller's already-proven bounded-thread lifecycle rather than re-implementing it. What `StateWatcher` adds — the one thing `SessionPoller` deliberately doesn't do — is change detection: a `StateReadResult` only reaches the caller's `on_change` callback when its `(status, state, error)` triple differs from the last one delivered, comparing full parsed content rather than the file's modification timestamp (a `--watch`-republished file with byte-identical content must never spam repeat callbacks). `on_change` exceptions are caught internally and optionally forwarded to `on_error` (itself also exception-safe) — a bug in a caller's callback can never silently stop future updates, since nothing here ever lets an exception reach `SessionPoller.poll_once()`, where an uncaught one would silently kill the background thread. No UI code, no League imports, no duplicated JSON parsing — every read goes through the injected `reader_fn` (default `read_runtime_state`).
42. `src/ui/presentation.py` — `build_presentation(app_state, name_lookup=None) -> dict`, the toolkit-independent transform of a `DraftRuntimeService`-shaped app-state dict into four stable render structures a future PySide6 layer (Stage 5+) will read but never recompute: `build_status_header` (one of four fixed title/message/severity/`show_content` templates keyed by `state`, with `processing_error`'s message filled from `app_state["error"]`, and an honest fifth "Unknown State" fallback for any future/unrecognized `state` value rather than crashing); `build_draft_summary` (phase name/time-left/role from `draft_snapshot`, `None` whole-section when there's no snapshot yet); `build_recommendation_cards` (one card per shared-schema recommendation entry, preserving `priority`/ordering and passing `details.score_breakdown` through **unchanged** — never recomputing a score — with malformed entries, i.e. missing any of `category`/`subject`/`recommendation`/`reason`/`severity`/`confidence`/`priority`, or non-dict entries silently skipped rather than rendered incompletely or crashing the whole batch); and `build_diagnostics` (`warnings`/`error`/`state_schema_version`/`champion_catalog_version` plus `unresolved_ally_ids`/`unresolved_enemy_ids`/`missing_ally_profiles` pulled from whichever recommendation entry's `details` happens to carry them, since every pick-recommendation entry in one poll shares the same snapshot-derived diagnostics). Champion-id-to-name resolution is the one place this module accepts an injected dependency, `name_lookup(champion_id) -> str | None`, because the published state only carries champion *ids* (recommendation entries already carry resolved names as their own `subject`/`recommendation` strings) and resolving an id needs the champion catalog, which this module deliberately never loads itself. No `name_lookup` given, or a `name_lookup` that returns `None` for an id it doesn't recognize, both degrade to an honest id-bearing label (`"Champion ID 22"` / `"Unknown champion (ID 9999)"`) — never a guessed name. Verified never to mutate its input `app_state` (a dedicated test deep-copies the input, calls `build_presentation()`, and asserts equality afterward). No PySide6 import, no filesystem access, no League API logic.
43. `demo/states/*.json` + `src/ui/demo_fixtures.py` (new — Stage 4) — five hand-authored, deterministic application-state fixtures (`01_league_client_unavailable`, `02_idle_no_champ_select`, `03_champ_select_prelock_recommendations`, `04_champ_select_locked_callouts`, `05_processing_error`), one for each of the four runtime states plus both `champ_select_active` sub-shapes (`pick_recommendation` entries and locked-champion `counter_warning`/`favorable_matchup`/`ally_synergy` callouts) — chosen deliberately so a future `--demo` mode (Stage 7) can cycle through a state that exercises every branch of `build_presentation()` at least once. Every fixture is shaped exactly like `DraftRuntimeService.poll_once()`'s real output and every embedded recommendation entry matches the real shared-schema shape (`recommend_draft()` would build the same keys) — verified by a dedicated test that runs `validate_state_shape()`/`validate_recommendation()` (the *real* validators, not new demo-specific ones) against every fixture. Illustrative-only content: champion names/ids are sample data (matching this checkpoint's own established filler names — Malphite, Zed, Nautilus — already used elsewhere in this doc as generic non-authored-profile examples), not real captured League data, no real player data, no new champion knowledge authored. `demo/states/` lives outside both `tests/` (these are also a runtime asset the shipped app will load, not test-only data) and `reports/` (not generated/regenerable output — these are checked-in, hand-authored, version-controlled sample data, so **not** added to `.gitignore`). `src/ui/demo_fixtures.py` provides `list_demo_state_files(directory=DEMO_STATES_DIR)` (glob, sorted by filename for deterministic cycling order) and `load_demo_states(directory=DEMO_STATES_DIR) -> list[dict]` (parses + validates every fixture, raising `ValueError` naming the offending filename for a malformed fixture — an authoring bug in this project's own demo data, not an honestly-expected absence). No PySide6 import, no network, no real League installation anywhere in this stage.
44. `src/ui/widgets/{status_header,draft_summary,recommendations,diagnostics}.py` + `src/ui/main_window.py` + `src/ui/app.py` (new — Stage 5; `PySide6>=6.7,<7.0` added to `requirements.txt`, already installed and import-verified in offscreen mode as `6.11.1` before this stage began) — the first real GUI code in this project. Each widget renders exactly one of `build_presentation()`'s four sections and nothing more: `StatusHeaderWidget.update_header(header)`, `DraftSummaryWidget.update_summary(summary_or_None)` (hides itself via `setVisible(False)` when there's no active snapshot), `RecommendationListWidget.update_cards(cards)` (rebuilds one `QLabel` per card every call — the count and content both change between polls, unlike the other three widgets' fixed-shape updates — never re-sorts or re-filters what it's given), and `DiagnosticsWidget.update_diagnostics(diagnostics)` (deliberately never hides an error/warning/unresolved-id line by default, matching `UI_DESIGN.md`'s "an `unavailable` marker must never be styled the same as checked-and-fine" rule one layer down from styling: not hidden at all). `MainWindow(QMainWindow)` assembles all four into one vertical layout and exposes exactly two update entry points: `update_presentation(presentation_dict)` (the direct, already-built-by-`build_presentation()` path) and the convenience `update_from_app_state(app_state, name_lookup=None)` (calls `build_presentation()` internally, for a future caller — Stage 6's watcher callback — that only has the raw app-state dict). `src/ui/app.py` splits into two non-blocking factory functions the automated suite exercises directly — `build_application(argv) -> QApplication` (reuses `QApplication.instance()` if one already exists, rather than raising the `RuntimeError` a second `QApplication()` construction would) and `build_main_window(app_state=None, name_lookup=None) -> MainWindow` — plus a thin, deliberately untested `main()` that calls `window.show()` and blocks on `app.exec()`, mirroring `src/draft/cli.py`'s established "thin `main()`, tested building blocks underneath" shape. No data source, no `StateWatcher` wiring, and no CLI argument parsing exist yet (Stages 6–7) — this stage only builds the window itself and proves it can render every shape `build_presentation()` produces. Every test (`test_ui_widgets`, `test_main_window`, `test_app`) runs with `QT_QPA_PLATFORM` forced to `offscreen` via `os.environ.setdefault(...)` **inside the test file itself, before the first PySide6 import** — not relying on an external environment variable the test runner might forget to set — and never calls `.show()` or `.exec()`, so the whole suite stays non-interactive and finite. Widget visibility is asserted via `.isHidden()` (reflects an explicit `setVisible()` call regardless of whether any top-level window was ever shown), not `.isVisible()` (which requires the whole ancestor chain to be shown on screen and would read `False` for every widget in this offscreen, unshown-window test suite regardless of what the widget itself was told).
45. `src/ui/live_state_source.py` (new — Stage 6) — `LiveStateSource(QObject)`, the thread-safe bridge between `StateWatcher`'s background-thread polling (Stage 2) and Qt's main-thread event loop. Wraps a `StateWatcher` internally (`watcher_factory=StateWatcher`, injectable) and re-emits every `on_change` delivery as a Qt `Signal(object)` (`state_changed`, carrying the raw `StateReadResult`) rather than calling into any widget directly. This is the actual mechanism that makes cross-thread delivery safe: `LiveStateSource` itself is constructed on (and so has Qt thread-affinity to) the GUI thread, while `StateWatcher`'s `on_change` fires from `SessionPoller`'s background thread — Qt detects that mismatch at `emit()` time and automatically queues the connected slot's invocation onto the GUI thread's event loop instead of running it inline on the polling thread, so a slot connected to `state_changed` is *always* safe to touch widgets from, with zero manual locking or `QMetaObject.invokeMethod` boilerplate required in this module or its caller. `src/ui/main_window.py` gained the counterpart consumer, `MainWindow.update_from_state_result(result, name_lookup=None)`: for `status == VALID_STATE` it delegates straight to the existing `update_from_app_state()`; for the four *reader*-level statuses `build_presentation()` was never meant to know about (`file_missing`/`invalid_json`/`invalid_state_shape`/`read_error`), it renders an honest status-only header from a small `_READ_RESULT_HEADERS` table (`file_missing` is `severity: "low"` — an expected, not-yet-started condition; the other three are `"high"` and always surface the real `result.error` text verbatim, never swallowed) with the other three sections cleared (`draft_summary: None`, empty `recommendation_cards`, an empty-but-honest `diagnostics`) — deliberately kept in `main_window.py` rather than teaching `presentation.py` about `StateReadResult`, so `presentation.py`'s documented "takes a `DraftRuntimeService` app-state dict" contract stays exact. `src/ui/app.py`'s `main()` now actually wires this up end-to-end against the default runtime path (`LiveStateSource()` → `state_changed.connect(window.update_from_state_result)` → `source.start()`), with `app.aboutToQuit.connect(lambda: source.stop())` so the background polling thread is always stopped when the window closes rather than leaking past process shutdown — still no CLI argument parsing (`--state-file`/`--demo`/etc. remain Stage 7), just a zero-config default. Tests (`test_live_state_source.py`, 4; `test_main_window.py` gained 5 more) split into a fast direct-wiring check (a fake `watcher_factory` whose captured `on_change` is invoked synchronously in-thread, proving the signal-emission wiring itself with zero real threading) and one real-threading integration test (a real `StateWatcher` against a real temp file, with `QCoreApplication.processEvents()` pumped in a small bounded wait loop — matching this project's established real-but-bounded-threading precedent, extended here to also satisfy Qt's requirement that *something* spin the event loop for a queued cross-thread signal to actually be delivered without a full blocking `app.exec()`) proving genuine cross-thread delivery, not just the wiring. Re-run 5x during development with no flakes observed.
46. `src/ui/demo_publisher.py` + `src/ui/app.py` CLI wiring (new — Stage 7) — `python -m src.ui.app` gained real argument parsing: `--state-file PATH`, `--demo`, `--demo-state NAME`, `--demo-interval SECONDS` (default `5.0`), `--verbose`, via `build_arg_parser()` (thin, directly testable, same shape as `src/draft/cli.py`'s own parser). `DemoStatePublisher(QObject)` is the new piece: a `QTimer`-driven cycler that writes each `demo/states/` fixture (Stage 4) through the *real* `publish_state()` writer — `--demo` mode deliberately never bypasses the real `LiveStateSource`/`StateWatcher`/`MainWindow.update_from_state_result()` pipeline (Stage 6) for a second, demo-only rendering path; it only changes *what's being published and where*. `start()` always publishes the first fixture immediately (no waiting a full interval to see anything) and only starts the repeating timer at all when given more than one state — `--demo-state NAME` (pinned to exactly one fixture via the new `load_demo_state_by_name()` in `demo_fixtures.py`, matched by filename stem with or without `.json`, raising `ValueError` listing the available names for a typo) therefore never spins a needless timer. Tests (`test_demo_publisher.py`, 5; `test_demo_fixtures.py` gained 4 more for `load_demo_state_by_name`; `test_app.py` gained 12 more for the parser/`resolve_state_path`/`build_demo_publisher`) use the same fast-fake-plus-real-`QTimer`-integration split established in Stage 6 — the real-timer cycling test pumps `QCoreApplication.processEvents()` in a bounded wait loop exactly like `test_live_state_source.py`'s pattern. Re-run 5x during development with no flakes observed.

## 3. Current Limitations

- **No real benchmark data exists.** The entire `src/benchmark/` system is verified foundation only — no Challenger/pro/patch data has been scraped or entered, by explicit instruction. `coaching_session.json`'s benchmark section will read `"unavailable"` for every match until a real source is wired in.
- **Benchmark metrics are limited to whole-game averages.** Minute-10-specific metrics (`cs_10`, `gold_10`, `deaths_before_10` — the original illustrative example) aren't computable without parsing timeline `participantFrames`, which `timeline_analyzer.py` doesn't currently do and wasn't modified to do (out of scope, protected file). `METRIC_DIRECTIONS` currently only has real support for `cs_per_minute`/`gold_per_minute`/`kill_participation`/`damage_to_objectives`/`vision_score`/`death_count`.
- **No patch tracking on the player's side.** `analyzer.py` doesn't extract `gameVersion`, so patch-filtered benchmark lookup can't be meaningfully exercised yet; `find_benchmarks()` is called with `patch=None`.
- **The AI layer's free-by-default backend (per `ROADMAP.md` §1) still isn't built.** `src/ai/client.py`'s paid Anthropic path is the only backend that exists; it's opt-in, never called automatically by anything, but the *deterministic* backend that should be the actual default hasn't been implemented yet.
- **Storage is flat JSON, not SQLite** — still a deliberately flagged, still-unresolved decision per the original checkpoint; unchanged this pass.
- **Knowledge coverage is narrow by design** (5 champions' worth of coaching notes, 2 roles, 4 champions' worth of item knowledge, 5 champions' worth of the new draft-profile knowledge) — see `KNOWLEDGE_SYSTEM_PLAN.md` for the intended incremental-growth strategy (grow from real opponents faced, not exhaustive upfront authoring). The 5 draft-profile files (`{yone,akali,fizz,syndra,pyke}_profile.md`) cover only the player's own pool — no opponent has a profile yet, same tier-1-first gap the coaching/item knowledge already had before this checkpoint.
- **`knowledge/champions/` now holds two independent record types per pool champion** — the pre-existing `{champion}.md` (macro-coaching notes, `loader.py`) and the new `{champion}_profile.md` (draft knowledge, `champion_loader.py`). They don't collide (different filenames, different loaders, different callers), but a future contributor skimming the directory should know these are deliberately separate, not a duplicate/stale pair.
- **No live game state, no overlay UI, no conversational coaching, no local model backend** — all deliberately deferred; full designs exist in `LIVE_SYSTEM_DESIGN.md` and `UI_DESIGN.md` but nothing in those documents is built.
- **No draft or rune system exists.** `knowledge/runes/`, `knowledge/drafting/`, and any pick/ban/synergy recommendation logic are all still design-only (`ROADMAP.md` §2–4). `src/draft/` has a real data client and a real snapshot builder, but no decision logic of any kind sits on top of either.
- **`src/live/` remains fully unstarted**, and `src/draft/` has only data access — `LCUClient` (raw fetch) and `build_draft_snapshot()` (raw → normalized dict), no pick/ban/synergy logic, no rune logic, no UI. `SessionPoller` has now been exercised against one real data source (`LCUClient`), but only in tests, using fake lockfiles and mocked HTTP responses — it has never been run against a real, installed League client, and `build_draft_snapshot()`'s fixtures are hand-built to a plausible LCU shape, not captured from one either (see Sec.4 below). Wiring the Stage-1 adapters into `coaching_report.py` (an earlier checkpoint) also still only exposes a shared-schema *view* of the two existing systems' output — it does not build a second real system against the schema natively, which `RECOMMENDATION_SYSTEM_DESIGN.md`'s Stage 2 still requires before retiring the adapters.
- **The locked-champion path (`counter_warning`/`favorable_matchup`/`ally_synergy`) only ever surfaces facts already sitting on the current player's own champion profile.** It has no knowledge of enemy-vs-enemy or ally-vs-ally relationships and no full-team synergy/counter scoring — unchanged this checkpoint. It can only produce a `counter_warning`/`favorable_matchup` entry when the *enemy* pick's name happens to appear in one of the player's own `common_counters`/`favorable_matchups` lists — it cannot yet say anything when the player is on, say, Akali and the enemy picks a champion Akali's profile doesn't mention.
- **The pre-lock pick-recommendation path (`pick_recommendation`) scores four signals** (ally-side damage balance, direct synergy; enemy-side favorable matchup, common-counter risk, added this session) — still no positional/lane-matchup awareness, no consideration of what the enemy team is likely to draft *next* (only already-locked picks), and no cross-candidate comparison beyond independent scoring (a candidate never "knows" about another candidate). It also can't recommend anything the discovered candidate pool doesn't cover.
- **Champion-profile coverage is still only the player's own 5-champion pool.** Both `recommend_draft()` paths are bottlenecked by this: the locked-champion path needs the *enemy*/*ally* pick's name in the player's own profile lists, and the pick-recommendation path's default candidate pool (`list_available_champion_profiles()`) can only ever surface those same 5 champions — a real 5v5 champ-select session will very often have every locked ally/enemy pick and most pick candidates resolve to "no authored profile," honestly degrading (`details.missing_ally_profiles`, or simply nothing to recommend) rather than fabricating anything. Expanding profile coverage (per the prior checkpoint's tier-2 recommendation) directly increases how often either path has anything to say.
- **`recommend_draft()` has never been exercised against a real `DraftSnapshot` built from a real `LCUClient` session** — only against hand-built snapshot fixtures and the real `champion_catalog`/`champion_profile` data it's designed to consume. The same "sanity-check the real LCU response shape by hand" gap flagged in the prior two checkpoints still applies here, one layer further downstream.
- **The champion-ID catalog (`data_dragon.py`) has never been fetched from the real Data Dragon champion.json endpoint** — `build_champion_catalog()`'s shape (keying off `"key"`/`"name"`, handling the id-slug-vs-display-name distinction) is verified against a hand-built fixture matching Data Dragon's publicly documented schema, not a live fetch. Same category of gap as the LCU response-shape assumption above, for a different endpoint.
- **`DraftRuntimeService`/`publish_state()` have run for real exactly once, in the `league_client_unavailable` state only.** `python -m src.draft.cli --once` was manually smoke-tested on this development machine (no League client installed) and correctly produced a real, valid `reports/runtime/draft_state.json`. That only exercises the "client not running" branch — the `idle_no_champ_select`, `champ_select_active`, and `processing_error` branches, and the real `LCUClient`/Data Dragon calls a genuine champ-select session would trigger, remain unverified against anything real. Every automated test still uses hand-built fakes.
- **`python -m src.ui.app` (real mode or `--demo`) has never been manually run end to end on this machine — only exercised by automated, offscreen tests.** Real mode has never been pointed at the real `reports/runtime/` directory while `src/draft/cli.py --watch` is actually running concurrently; `--demo`/`--demo-state` have never been visually confirmed to actually cycle/display in a real (non-offscreen) window. `build_presentation()`'s `name_lookup` champion-id resolution has only ever been tested with hand-built fake lookups, never a real `champion_name_from_id`-backed catalog closure — `main()` still passes no `name_lookup` at all, so every champion in a live or demo window today renders as an honest `"Champion ID N"` label, never a resolved name. Wiring a real loaded champion catalog through `main()` is explicitly still open (see Sec.4).
- **No manual visual verification of the desktop UI has happened at all, even after Stage 9's hardening pass** — every widget/window test still only inspects Qt object state (label text, `isHidden()`, child widget presence/type, `minimumSize()`) in offscreen mode; no screenshot, no human has looked at the rendered window, no spacing/margins/font sizing has been eyeballed. Stage 9 added a `QScrollArea` for the recommendation list and a sane default window size based on reasoning about what a desktop window needs, not from looking at one — this closes the most obvious structural risk (an unbounded list breaking the layout) but is not the same as a real usability pass. This remains an open gap between "the tests pass" and "the window looks and works well for an actual user" until someone runs `python -m src.ui.app --demo` on a real display.
- **`--capture-once` has never captured a real champ-select session.** Manually smoke-tested only against the "no active session" path (nothing written, as designed) — the actual sanitization logic (`sanitize()`) is thoroughly unit-tested against hand-built fixtures shaped like a real LCU response, but the real response shape it's specifically built to validate against remains genuinely unconfirmed. This is the honest, expected state of the one tool whose entire purpose is closing that gap — it can't close the gap until someone runs it against a real League client.
- **`sanitize()`'s sensitive-key list is a fixed, named set, not exhaustive.** It covers every field this project's design docs and public LCU documentation currently name as identifying (`puuid`, `summonerId`, `password`, etc.), but a real captured file should still be reviewed by hand before sharing — the tool says so in the file itself (`CAPTURE_FILE_WARNING`), deliberately not claiming a guarantee it can't back up.

## 6. Architectural Decisions That Should Not Be Changed Without Explicit Confirmation

Carried forward from the original checkpoint (still true, unchanged this session):

- **Riot API is the sole source of truth for match data.** Data Dragon is the sole source of truth for static item data. No OP.GG/U.GG/Lolalytics scraping — supplementary only, never foundational, and still not implemented anywhere.
- **Rule-based analysis and AI coaching are separate layers.** Every fact-finding module must stay deterministic and explainable; the AI layer only phrases already-computed findings, never decides what they are.
- **Missing data is marked, never fabricated.** `"unavailable"`, `"insufficient_data"`, `null` are load-bearing signals throughout — extended this session to `src/benchmark/` (a metric with no known direction, or no player data, reports `"unavailable"`, never a guessed score) and `src/coaching/` (missing item recommendations, missing benchmark data, both stay honestly absent).
- **API keys live only in `.env`**, never printed/logged, gitignored.
- **`game_history.json` upserts by `match_id`**; `src/benchmark/storage.py` and `src/coaching/`'s file lookups follow the same upsert/no-duplication discipline.
- **Champion/role/item knowledge is qualitative markdown, hand-curated**, not numeric thresholds.
- **The JSON-vs-SQLite storage choice is still flagged but unresolved.**
- **New entrypoints wrap existing logic instead of duplicating it** (`backfill.py` calling `importer.run_import()` unchanged is the original example; `src/coaching/coaching_report.py` combining already-computed JSON without re-deriving anything is this session's continuation of the same rule).

New decisions established this session:

- **`GameSnapshot`'s "independent of data source" principle was deliberately reapplied to benchmarks.** `src/benchmark/comparison.py` operates on plain dicts and has no idea whether a benchmark came from a future scraper, a manual entry, or a patch-aggregate import — the same reasoning that made `game_state.py` reusable for a future live-data builder without any downstream changes.
- **Benchmark comparisons are informational only and must never become coaching priorities.** `src/coaching/priorities.py` never imports `src/coaching/benchmark_section.py` or reads its output. This is enforced by a test (`test_benchmark_gaps_never_become_coaching_priorities`) that asserts `main_lessons`/`next_game_focus` are byte-identical whether or not benchmark data is present — not just a docstring claim.
- **A metric registry (`METRIC_DIRECTIONS`) is a deliberate, small, code-level scaling ceiling** — the same tradeoff already accepted for `item_recommender.py`'s `TRIGGER_KEYWORDS` (see `ARCHITECTURE_AUDIT.md` Finding E). Adding a new benchmark metric means adding one dict entry, not touching comparison logic.
- **Wiring a new analysis step into the automatic import flow means adding one composition function to the owning analysis module and one call site in `importer.py`, never inline logic in `importer.py` itself.** `item_recommender.generate_item_recommendations()` (composing `build_snapshot_from_match` + knowledge loading + `recommend_items`) is the concrete precedent for this — the same "importer orchestrates, modules analyze" rule already established for `analyze_match()`/`macro_analyze()`, now proven out a second time for a genuinely different analysis pipeline.

New decisions established this checkpoint (the recommendation-system pivot):

- **AI is optional and explanation-only, project-wide, not just for post-game coaching.** Any future draft/rune/live explanation feature must reuse `src/ai/prompt_builder.py`/`validator.py`'s existing grounding pattern — one AI wrapper for the whole project, never a new one per domain.
- **A shared recommendation contract (`src/recommendations/schema.py`) exists, and Stage-1 adapters (`src/recommendations/adapters.py`) now translate both existing systems onto it.** `item_recommender.py` and `coaching/priorities.py` keep their current output shapes completely unchanged — the adapters are additive pure functions, not called by anything in the pipeline yet. A native-format Stage 2 migration (retiring the adapters, having `recommend_items()`/`select_priorities()` emit the shared shape directly) is explicitly deferred until a second real system (draft or rune) has proven the schema out. Do not force Stage 2 prematurely, and do not wire the Stage-1 adapters into the live pipeline without deciding that deliberately (see Next Milestone).
- **When a source system doesn't distinguish two axes the shared schema keeps separate, the adapter reuses one value for both rather than inventing a new derivation.** Both `adapt_item_recommendation()` and `adapt_macro_lesson()` set `severity` equal to `confidence`, since neither `item_recommender.py` nor `priorities.py` computes impact/urgency independently of data-quality confidence today. This is deliberately conservative — a translation layer should never manufacture information its source doesn't have, even to fill a field the target schema expects.
- **`confidence` (data quality) and `severity` (impact/urgency) are two distinct axes going forward**, resolving `ARCHITECTURE_AUDIT.md` Finding C's three-incompatible-vocabularies problem for any *new* system built against the shared schema. Existing systems (`macro_analyzer.py`'s `confidence`/`tier`, `item_recommender.py`'s `confidence_tier`/`confidence_score`) are not retrofitted — only the adapters translate into this vocabulary, per the point above.
- **`src/draft/` and `src/live/` are not started.** Per explicit instruction this checkpoint, only the shared contract was built — no champion-select or live-client integration exists yet.

New decisions established this checkpoint (Stage-1 wiring):

- **`coaching_report.py` is the correct place to call the adapters, not a new module.** It already combines already-computed JSON from multiple sources (`_item_review()` is the existing precedent for a small combination helper living directly in this orchestrator); calling two existing pure functions and concatenating their output is coordination, not new recommendation logic, so it doesn't violate "modules perform logic, orchestrators coordinate."
- **`shared_recommendations` adapts every item recommendation, not just the top-3 `item_review.top_recommendations` slice.** The two views are independent and serve different consumers — `item_review` is the existing truncated display view, `shared_recommendations` is the full-fidelity shared-schema view a future cross-system consumer (overlay, draft/rune aggregator) would read. Truncation stays local to `_item_review()`, not duplicated into the new helper.

New decisions established this checkpoint (shared polling/runtime foundation):

- **`src/runtime/poller.py` is intentionally the only thing this checkpoint built.** No LCU client, no Live Client Data API client, no `DraftSnapshot`, no draft/rune/live logic — `SessionPoller` is exercised only against fake, hand-built data sources in `tests/test_runtime_poller.py`. Per explicit instruction, real data sources and any analysis on top of them are separate, future work.
- **The data-source contract is a bare zero-argument callable returning `dict | None`, not a class or protocol.** This is the same "operates on plain dicts, doesn't know where they came from" discipline already established for `GameSnapshot` (`src/analysis/game_state.py`) and `src/benchmark/comparison.py` — a future LCU client or Live Client API client just needs to be *a callable*, nothing more, to be a valid `SessionPoller` data source.
- **`poll_once()` is the single synchronous unit both the background thread and any future external caller go through.** This was a deliberate design choice specifically so a future desktop app (Qt/Tk) can drive polling from its own timer/event loop by calling `poll_once()` directly, without ever touching this module's background thread — avoids the common desktop-app pitfall of updating UI state from a non-UI thread, without needing two separate code paths to keep in sync.
- **Idle vs. active state is presence-of-a-result, not any inspection of the result's contents.** `state` is `"idle"` when `last_result is None`, `"active"` otherwise — `SessionPoller` never looks inside the dict a data source returns. Interpreting *what kind* of session is active (champ select vs. live game) is explicitly left to the caller, not this module — keeping it domain-blind per this checkpoint's instructions.
- **Tests exercise the real `threading`-based `start()`/`stop()` loop, not just `poll_once()` in isolation, but bound every real sleep to tens of milliseconds and cap `stop()`'s join with a timeout.** This was a deliberate choice to actually prove the loop mechanism works (interval passed to `sleep_fn` matches configuration, `is_running` flips correctly, repeated `start()`/`stop()` calls are idempotent) rather than only testing the thread-free `poll_once()` unit, while still guaranteeing every test terminates in well under a second even if the loop logic were broken.

New decisions established this checkpoint (LCU client — `src/draft/` foundation):

- **`404` and connection errors both mean "no session right now," but anything else (a `500`, malformed JSON) is left to raise, not silently become `None`.** `get_champ_select_session()` deliberately distinguishes "honestly nothing to report" (matches the project's `"unavailable"`/`null` discipline) from "something is actually broken" (should surface as an error, per the same discipline that already governs `item_recommender.py`'s Data Dragon cross-check flagging unrecognized items rather than silently dropping them).
- **`LCUClient`'s HTTP call is injected via a `get_fn` parameter, not a mocking library or a `requests.Session` subclass.** This directly reuses `src/riot/data_dragon.py`'s existing `get_fn`-injection precedent (`load_item_catalog(static_dir, get_fn=...)`) instead of introducing a second dependency-injection style for HTTP calls in the same codebase.
- **`LCUClient` is a class, not a bare function, specifically so an instance is directly usable as `SessionPoller`'s `data_source`.** `SessionPoller` only requires a zero-argument callable (see the prior checkpoint's decision that the data-source contract is "a bare callable, not a class or protocol") — `LCUClient.__call__` satisfies that contract without `functools.partial` or a wrapper lambda at the call site, while `get_champ_select_session()` stays available as an explicit, independently-testable method name.
- **The real `/lol-champ-select/v1/session` response shape is assumed, not verified, by this checkpoint.** All fixtures (`CHAMP_SELECT_SESSION` in `tests/test_draft_client.py`) are hand-built to a plausible shape based on Riot's public LCU documentation, not captured from a real running client — flagged explicitly in Sec.4 above as something to sanity-check by hand before building `DraftSnapshot` on top of it, the same "don't silently assume, state the gap" discipline used throughout this project's limitations sections.
- **No default lockfile path is configurable via `.env` yet.** `DEFAULT_LOCKFILE_PATH` is a hardcoded standard Windows install path (`C:/Riot Games/League of Legends/lockfile`), always overridable via `LCUClient(lockfile_path=...)` (which is how every test uses it) — a real caller on a non-default install location would need to pass this explicitly today. Not wired to `.env`/`player_profile.json` since nothing yet calls `LCUClient()` with its defaults outside of tests.

New decisions established this checkpoint (`DraftSnapshot`):

- **`build_draft_snapshot()` is a plain function returning a plain dict, not a dataclass or a `DraftSnapshot` class**, deliberately mirroring `build_snapshot_from_match()`/`GameSnapshot` in `src/analysis/game_state.py`, which also returns a plain nested dict rather than a typed object. Consistency with the one existing precedent for "source-agnostic snapshot" mattered more here than introducing a new pattern.
- **`ally_team`/`enemy_team` (full 5-slot rosters with `None` for unpicked slots) double as "team compositions"; `ally_picks`/`enemy_picks` are a separate, derived flat-list convenience view of only the locked-in champion IDs.** Rather than adding a third, redundant `team_compositions` key, the roster lists already are the composition — the flat pick lists are computed from them, not maintained independently, so there is exactly one place a pick could ever disagree with a roster entry (nowhere; there's only one source).
- **`build_draft_snapshot(None)` and `build_draft_snapshot({})` both return `None`, not an empty-but-present snapshot.** This mirrors `SessionPoller`'s own `state` convention (`"idle"` when `last_result is None`) established the prior checkpoint — a `DraftSnapshot` consumer downstream can treat "no snapshot" as the single honest signal for "no champ-select session," without needing to separately check for an all-empty snapshot.
- **The LCU's `championId: 0` and blank `assignedPosition: ""` are both normalized to `None`,** not passed through as their raw sentinel values, so nothing downstream needs to know the LCU's own "nothing here" conventions — the same translation responsibility `game_state.py` already takes on for post-game data (e.g. `current_gold: None` since it isn't derivable from a completed match, rather than leaving callers to infer that from an absent key).
- **Fixtures in `tests/test_draft_snapshot.py` are hand-built to a plausible real LCU response shape (based on Riot's publicly documented LCU schema), not captured from a real running client.** Flagged explicitly in Sec.3/4 above as an open gap to close by hand before this foundation is trusted for real recommendation logic — consistent with this project's "state the gap, don't quietly assume" discipline used throughout the checkpoint's limitations sections.

New decisions established this checkpoint (champion knowledge foundation):

- **The new draft-knowledge record type gets its own filename (`{champion}_profile.md`) in the same `knowledge/champions/` directory, rather than a new directory or an extension of the existing `{champion}.md` files.** Editing the existing coaching files in place was rejected even though `loader.py`'s parser would have safely ignored unrecognized new sections (it only captures headings present in `SECTION_KEYS`) — coexistence-by-filename keeps each file single-purpose and independently readable, and creating a whole new top-level directory was rejected as an unnecessary structural split for what is still fundamentally "knowledge about a champion." This is the same "sibling loader, different shape" precedent `item_loader.py` established relative to `loader.py`, now applied to file-naming as well as to loader structure.
- **`champion_schema.py` is a separate file from `champion_loader.py`, mirroring the `benchmark_schema.py`/`storage.py` and `recommendations/schema.py`/`adapters.py` splits already established twice in this codebase**, rather than folding `validate_champion_profile()` directly into the loader. This keeps the shape-and-validation-only piece independently testable and reusable by a future system that builds champion profiles some other way (e.g. a scaffolding script per `KNOWLEDGE_SYSTEM_PLAN.md`'s noted-but-not-built skeleton-generator idea) without needing the markdown parser at all.
- **A missing profile file returns `None`; a malformed *existing* one raises `ValueError`.** Same "absence vs. corruption" split `src/draft/client.py` draws for LCU lockfiles (no lockfile → `None`, malformed lockfile → `LockfileFormatError`) — a champion simply not having a profile yet is expected and common (see `KNOWLEDGE_SYSTEM_PLAN.md`'s tiered-coverage strategy), but a profile file that exists and fails validation is a real hand-authoring mistake that should surface immediately rather than silently propagate a broken dict downstream.
- **`VALID_ROLES` and `VALID_DAMAGE_TYPES` reuse existing project vocabularies instead of inventing new ones.** Roles reuse Riot's `teamPosition` values (already load-bearing in `game_state.py`/`loader.py`'s `ROLE_FILENAME_MAP`); damage types reuse `data/static/champion_damage_types.json`'s existing `physical`/`magic`/`hybrid`/`unknown` set. A second, slightly-different vocabulary for the same real-world concept would have forced a translation layer somewhere for no benefit.
- **The champion's canonical name comes from the file's own `# Heading`, not from the loader's filename-derived caller argument.** Matches every other knowledge file's existing `# ChampionName` convention (`{champion}.md`, `{champion}.md` in `knowledge/items/`) and means a profile's `champion` field is authored data, not a side effect of how it happened to be looked up — `load_champion_profile("yone", ...)` and `load_champion_profile("YONE", ...)` both still produce `"champion": "Yone"` because the heading says so, not because of case-normalization logic in the loader.
- **This checkpoint deliberately stops at data format + loader + validation, with zero consumers.** No pick/ban recommendation, matchup scoring, synergy logic, or rune logic reads `load_champion_profile()`'s output yet, and `DraftSnapshot`'s champion-ID picks aren't joined against this schema's champion-name records yet either (flagged as an open gap in Sec.3) — both are explicitly separate, future work per instruction.

New decisions established this checkpoint (champion-ID catalog + first draft recommender):

- **The champion catalog is a second, independent lookup structure inside `data_dragon.py`, not a merge into the existing item catalog.** `build_champion_catalog()`/`load_champion_catalog()` are new functions with their own return shape and cache filename, sharing only `fetch_latest_version()`, `STATIC_DIR`, and the `get_fn`-injection pattern with the item catalog. A single combined "static data" catalog was rejected — items and champions are different domains with different lookup keys (name/id vs. name/id but semantically unrelated), and `load_item_catalog()`'s existing callers (`item_recommender.py`) must never need to know champions were added.
- **`champion_name_from_id()`/`champion_id_from_name()` are plain functions taking a catalog dict, not methods on a catalog class.** Matches every other lookup pattern already in this codebase (`find_benchmarks()`, `_category_for_pattern()`, etc.) — the catalog itself stays a plain dict, consistent with `build_item_catalog()`'s existing precedent, and callers that only need the raw dict shape (e.g. a future bulk operation) aren't forced through an object API to get it.
- **`recommend_draft()` intentionally does not attempt full-team synergy or counter scoring, even though the champion profiles now contain enough raw material (`common_counters`/`favorable_matchups`/`synergy_champions` on *every* champion, not just the current player's) to approximate it.** The current implementation only ever consults the *current player's own* profile, deliberately leaving cross-referencing every enemy pick's profile against every ally pick's profile (real team-composition analysis) to the dedicated `knowledge/drafting/` + draft/synergy recommender step `ROADMAP.md` §4 already scopes separately. Building that now would have been scope creep past "first deterministic draft recommendation engine."
- **Every locked-champion (`counter_warning`/`favorable_matchup`/`ally_synergy`) entry sets `recommendation: null`.** *(Updated the following checkpoint: this is true only for the locked-champion path — see below. It was originally written as a blanket rule before pick recommendations existed.)* These are informational warnings/callouts ("this enemy counters you," "this ally synergizes with you"), not prescriptive actions — inventing a prescription this narrow engine has no basis for computing would violate the "never fabricate" discipline just as much as inventing a fact would.
- **`recommend_draft()`'s own internal `validate_recommendation()` check raises on failure rather than filtering the bad entry out.** Consistent with `champion_loader.py`'s "malformed data is a bug, not an absence" precedent — a recommender producing a schema-invalid entry means this module has a bug, and silently dropping the bad entry would hide that bug instead of surfacing it. Still true for both paths this checkpoint added.

New decisions established this checkpoint (pre-lock pick recommendations — correcting the draft-pick milestone gap):

- **`recommend_draft()` dispatches internally rather than becoming two separate public functions.** `current_player.champion_id`'s presence is already the one fact that distinguishes "comment on a pick" from "help make a pick" — callers (a future `SessionPoller.on_result`, a CLI, a UI) always have a `DraftSnapshot` and want "whatever's relevant right now," not a decision about which of two functions to call. `_recommend_for_locked_champion()`/`_recommend_champion_picks()` stay as separate internal functions so each path's logic is independently readable and testable, but there is exactly one public entry point.
- **Pick recommendations set `recommendation: <champion name>`, unlike the locked-champion path's `null`.** This is a deliberate, principled difference, not an inconsistency: a `pick_recommendation` entry's entire purpose is to say "consider this champion" — that *is* an actionable recommendation the engine has a real, inspectable basis for (role fit, and optionally damage balance / direct synergy), unlike the locked-champion callouts, which only ever state an observed fact about a pick someone already made.
- **Role fit is a hard filter, never a scored bonus.** A candidate that doesn't support the assigned role is excluded before scoring even begins, not merely down-ranked — matching the explicit instruction that role fit is "required, not merely bonus." `details.score_breakdown.role_fit` is always the literal string `"required"`, never a number, so nothing could misread it as a variable score component.
- **Damage-balance and direct-synergy bonuses are both named integer constants (`DAMAGE_BALANCE_BONUS = 2`, `DIRECT_SYNERGY_BONUS = 1`) with no further tuning knobs, and `details.score_breakdown` always reports each component plus their `total`.** This was a deliberate "keep it small and fully inspectable" choice per explicit instruction — no weighting curve, no normalization, no decay, nothing that would require reading this module's source to understand why one candidate outranked another. Every ranking decision is reconstructible from the returned entry alone.
- **Direct synergy is a flat bonus, not scaled by how many locked allies match.** A candidate synergizing with two locked allies scores the same `DIRECT_SYNERGY_BONUS` as one synergizing with one — matching "add a score only when the candidate profile explicitly lists a locked ally," not "add a score per match," which would have been an invented scaling rule the instructions never asked for.
- **`strengths`/`preferred_playstyle` are copied into `details` for transparency but never scored**, per explicit instruction that a longer list must not itself earn points — verified by a dedicated test (`test_pick_recommendation_details_include_strengths_and_playstyle_without_scoring_them`) comparing two candidates with different-length `strengths` lists and asserting equal `total` scores.
- **Two distinct `"unavailable"` entries (`subject: "role_unavailable"` / `subject: "no_eligible_candidates"`) rather than an empty list, for the two "genuinely nothing to recommend" cases in the pick-recommendation path.** This deliberately differs from the locked-champion path's `[]`-on-absence convention (and from this same path's own `[]` when there's no `current_player` at all, or no `snapshot`) — per explicit instruction, "assigned role unavailable" and "no eligible profiles" must each surface as one schema-valid entry a consumer can render, not silently vanish into an empty list indistinguishable from "nothing to say because everything's fine."
- **`unresolved_ally_ids`/`missing_ally_profiles` are computed once per `recommend_draft()` call and copied into every returned pick entry's `details`,** rather than being a separate top-level return value. `recommend_draft()`'s return type must stay `list[dict]` of shared-schema entries — no secondary channel for "oh, and also here's some metadata" — so this context travels inside the one shape every consumer already knows how to read.
- **One existing test's *expectations* changed** (`test_no_current_player_champion_picked_yet_returns_empty_list` → `test_no_current_player_champion_picked_yet_triggers_pick_recommendations`), and no other existing test did. That test was specifically asserting the *old*, now-corrected gap ("no champion locked → `[]`, always") — updating it is completing this checkpoint's explicit correction, not a regression. Every other pre-existing `test_draft_recommender.py` test (all locked-champion-path behavior) required zero changes, confirming the locked-champion path's behavior is genuinely untouched.
- **`list_available_champion_profiles()` lives in `champion_loader.py`, not `recommender.py`.** Discovering which profile files exist on disk is a loading concern (same file, same responsibility as `load_champion_profile()`), not a recommendation-logic concern — `recommender.py` only ever calls it as a default, never re-implements directory scanning itself. Consistent with "modules perform logic, orchestrators coordinate": the recommender orchestrates candidate discovery, filtering, and scoring; the loader owns everything about what's on disk.

New decisions established this session (Stage 1 — conservative enemy-side draft signals):

- **`common_counter_risk` is stored as a positive risk *magnitude* in `score_breakdown`, then subtracted when computing `total`,** rather than being stored as a negative number directly. `{"common_counter_risk": 1}` reads as "1 point of risk" at a glance; a reader shouldn't have to remember a sign convention to understand a single field in isolation. `total = damage_balance + direct_synergy + favorable_enemy_matchup - common_counter_risk` is the one place the subtraction happens, and it's spelled out in this checkpoint and in the module docstring rather than left implicit.
- **Both new signals reuse the exact "flat bonus, not scaled by match count" rule `direct_synergy` already established**, rather than inventing a new scaling behavior for the enemy side. A candidate favorable against two locked enemies scores the same as favorable against one — consistent scoring semantics across every signal in this module, not a special case per signal.
- **Severity thresholds on `total` were deliberately left unchanged**, even though `total`'s possible range grew (now roughly -1 to 4 instead of 0 to 3). Rule 3 of this session's own instructions ("preserve all existing behavior") took precedence over re-tuning a threshold nothing asked to have re-tuned — revisit only if a future stage finds the existing high/medium/low split stops making sense against the wider range.
- **`locked_enemy_names` is included in every pick entry's `details`, unconditionally** — not only when a signal actually fires — mirroring "fully inspectable `score_breakdown`" to the broader claim: a consumer should be able to see *what enemy information this entry's score was computed against*, even when the answer is "the enemy roster, and none of it happened to match."
- **Enemy picks are deduplicated by name (not by id) before either signal runs**, via `list(dict.fromkeys(...))` on the already-resolved name list. Deduplicating post-resolution (rather than pre-resolution on raw ids) is correct even in the pathological case of two different unresolvable ids and one resolvable id all mixed together — only the resolved, meaningful names need dedup protection against double-counting.

New decisions established this session (Stage 2 — end-to-end draft runtime service):

- **`LCUClient.is_client_running()` is additive, not a reinterpretation of `get_champ_select_session()`'s existing `None` collapse.** The earlier checkpoint's decision that `404`/connection-error/no-lockfile all honestly mean "nothing to report" for *that specific endpoint* stands exactly as documented — this new method answers a different, narrower question ("is the lockfile present at all") that `DraftRuntimeService` needed and no existing method could answer without changing its contract.
- **`DraftRuntimeService` requires `session_source`/`client_running_check` with no default, but defaults everything else to the real project functions.** Mirrors `SessionPoller`'s own precedent exactly: a data source with no universally-safe default stays required; a pure function that's already safe to call (`load_champion_catalog`, `build_draft_snapshot`, `recommend_draft`, `load_champion_profile`) gets the same real-function default `recommend_draft()` already set for `profile_loader_fn`. Consistency of this pattern across the codebase means a reader who understands one module's DI defaults understands them all.
- **Four states, not two.** A simpler design could have collapsed `league_client_unavailable`/`idle_no_champ_select` into one "idle" state, matching `SessionPoller`'s own idle/active vocabulary — rejected because the task explicitly asked for the finer distinction, and it's genuinely useful for a future UI ("League isn't open" vs. "League is open, just not drafting" are different states a player would want to see differently).
- **Every external call is wrapped in its own individual `try`/`except`, not one broad `try` around the whole `poll_once()` body.** This was deliberate: a broad wrapper would still prevent a crash, but it would lose *which* step failed — the per-step wrapping means `_error_state()`'s message always names the specific dependency that raised, and a step's already-computed output (e.g. a snapshot built successfully before the catalog load fails) is preserved in the error state rather than discarded.
- **The champion catalog is cached after first success but every other per-poll value is recomputed from scratch every time.** This is the one deliberate exception to "no persistent state between polls," justified by the real-world fact that Riot's champion roster doesn't change mid-session (a patch mid-draft doesn't happen) — recomputing everything else fresh every poll is what makes "one failed poll never permanently breaks the service" true without needing any explicit reset logic anywhere.
- **`poll_once()`'s `SessionPoller`-compatibility is a structural/type-level claim, not a claim that `SessionPoller`'s idle/active tracking becomes meaningful when driven by this service.** Documented explicitly (module docstring, checkpoint, and a dedicated test) rather than left as an implicit surprise for a future reader who wires the two together and finds `poller.state` always says `"active"`.

New decisions established this session (Stage 3 — atomic local state publisher):

- **Serialize to a string via `json.dumps()` before opening any file, rather than streaming with `json.dump(state, f)` directly.** A serialization failure (an unserializable value in `state`) then fails before any temp file is even created, instead of leaving a partially-written temp file that would still need cleanup. Fail fast, fail with zero side effects.
- **The temp file lives in the *same directory* as the final target, not a system temp directory.** `os.replace()`'s atomicity guarantee depends on both paths being on the same filesystem — a system temp dir and the target directory could be on different drives/filesystems, which would silently break the atomicity guarantee this whole module exists to provide. `tempfile.mkstemp(dir=output_path.parent, ...)` guarantees they're always the same filesystem.
- **Validation is shape-only (are the seven documented keys present), not a re-derivation of `DraftRuntimeService`'s own state-classification logic.** This module has no opinion on whether `state: "champ_select_active"` is the *correct* classification for a given `draft_snapshot` — that decision was already made upstream; re-checking it here would duplicate logic across two modules for no benefit, the same "don't duplicate logic" discipline this project has followed throughout.

New decisions established this session (Stage 4 — runnable draft CLI):

- **`--watch` drives `DraftRuntimeService.poll_once()` in a plain synchronous loop, not `SessionPoller.start()`'s background thread.** `SessionPoller`'s threading exists so a caller can keep doing *other* work on the main thread while polling happens in the background (its own docstring names a future UI's event loop as the motivating case) — a blocking CLI command has no such other work; its entire purpose while running is to watch. Using a background thread here would only add a second thread's worth of shutdown/join complexity for zero benefit, and would make the "no infinite test loops" requirement much harder to satisfy without real (if bounded) threading, exactly the kind of trade-off `test_runtime_poller.py` already accepts for `SessionPoller` itself but this module didn't need to take on.
- **The task's "does not create a second independent polling architecture" constraint is satisfied by reusing `poll_once()` as the loop body, not by reusing `SessionPoller` specifically.** The loop itself (`while True: poll(); sleep()`) is not an architecture — it's the same one-line idiom `SessionPoller._run_loop()` already uses internally. What would have violated the constraint is reimplementing retry/backoff/idle-tracking/threading decisions a second time; this CLI does none of that, it only calls the existing `poll_once()`.
- **`run_once()`/`run_watch()` are plain functions taking an already-constructed `DraftRuntimeService`, not part of a class, and `main()` is the only place a real `LCUClient` gets constructed.** Mirrors `src/history/backfill.py`'s existing `backfill()`/`run_backfill_cli()`/`main()` split exactly — parsing and object construction live only in `main()`, so every other function stays trivially testable with plain fakes and no `argparse`/`sys.argv` involvement.
- **`reports/runtime/` was added to `.gitignore`, mirroring the pre-existing `reports/generated_reports/` pattern exactly (`reports/runtime/*` ignored, `!reports/runtime/.gitkeep` kept).** This is generated, regenerable output (a snapshot of whatever the League client happens to be doing right now) — the same category as every other `reports/` subdirectory already gitignored, not authored content that belongs in version control.

New decisions established this session (Stage 5 — sanitized champ-select capture tool):

- **`sanitize()` redacts by key *name*, at any nesting depth, rather than by an exact field path.** A path-specific sanitizer (e.g. "redact `myTeam[*].puuid`") would only be as good as this project's current, *unverified* assumptions about the real LCU response shape — exactly the assumptions this whole tool exists to check. Name-based redaction degrades gracefully even if a sensitive field turns out to live somewhere this project didn't anticipate.
- **Redacted values are replaced with a fixed placeholder, never deleted.** Deleting a sensitive key would hide whether it existed in the real response at all, which defeats the tool's actual purpose: comparing real field *names* and structure against this project's hand-built fixtures. `"[REDACTED]"` preserves the key so the structural comparison stays possible while the value itself never leaves the sanitizer.
- **`capture_champ_select()` also captures and sanitizes the normalized `DraftSnapshot`, even though `build_draft_snapshot()`'s own narrow allowlist extraction already makes it structurally safe (`cell_id`/`champion_id`/`assigned_position` only — never `puuid`/`summonerId`).** Sanitizing it anyway is a small, deliberate consistency choice — every file this tool writes goes through the same one code path, so there's exactly one thing to audit for correctness, not two slightly-different write paths to keep in sync.
- **The review-before-sharing warning is baked into the captured file's own JSON content (`_warning` key), not left as external documentation a user could miss.** A file that ends up shared or attached somewhere still carries its own warning wherever it goes — matches this project's broader "don't rely on someone having read the docs" discipline (e.g. `"unavailable"`/`null` being self-describing values rather than requiring a legend).
- **`--capture-once` joins the same `required=True` mutually-exclusive `argparse` group as `--once`/`--watch`, not a separate flag that could be combined with them.** A single poll is either "process it normally" or "capture it for fixture validation" — there's no scenario where both make sense in the same invocation, so making them mutually exclusive at the parser level prevents a confusing combination from ever being expressible, rather than needing to be checked and rejected at runtime.

New decisions established this session (desktop app, Stage 1 — runtime state reader):

- **`src/ui/` is a new top-level package for everything UI-independent as well as everything UI-dependent later** — `state_reader.py` (Stage 1), `state_watcher.py` (Stage 2), and `presentation.py` (Stage 3) all live here even though none of them import a GUI toolkit, alongside the eventual PySide6 code (Stage 5+). The unifying theme is "belongs to the desktop application," not "imports Qt" — splitting the toolkit-independent layers into a separate package from `src/ui/` would have added a directory boundary with no real architectural benefit, since `src/draft/`'s own precedent already mixes data-access (`client.py`), pure logic (`recommender.py`), and orchestration (`service.py`, `cli.py`) in one package.
- **The reader reuses `state_publisher.py`'s `validate_state_shape()` directly rather than defining its own shape check.** Two independent shape definitions for the same JSON contract would inevitably drift; importing the one that already exists keeps "what counts as valid runtime state" defined in exactly one place, matching this project's established "no duplicated logic" discipline.
- **`StateReadResult` is a `@dataclass(frozen=True)` with a `status` field holding one of five module-level string constants, not an `enum.Enum`.** Matches `DraftRuntimeService`'s existing string-constant-for-state convention (`LEAGUE_CLIENT_UNAVAILABLE`, etc.) rather than introducing a second status-representation style into the same conceptual pipeline.
- **`StateWatcher` (Stage 2) wraps a private `SessionPoller` instance by composition rather than subclassing it or reimplementing its threading loop.** `SessionPoller` already owns the proven start()/stop() thread lifecycle (idempotent, bounded shutdown, injectable `sleep_fn`); `StateWatcher` reuses it as-is via its `data_source`/`on_result` hooks and adds only what `SessionPoller` deliberately doesn't provide: deciding whether a new poll result is worth telling a caller about.
- **Change detection compares a `(status, state, error)` content tuple, not `modified_at`.** `src/draft/cli.py --watch` rewrites the state file on every poll even when nothing changed, so an mtime-based watcher would fire spurious callbacks on every tick; comparing content means a callback only fires when something actually changed.
- **`on_change` (and `on_error`) calls are wrapped in `try/except` inside `StateWatcher._handle_result`.** A bug in a future UI's callback must not silently kill the background polling thread; the watcher degrades to reporting the exception via `on_error` (if provided) and keeps polling, rather than propagating into `SessionPoller`'s thread and stopping delivery of all future updates.
- **`presentation.py` (Stage 3) accepts champion-id resolution as an injected `name_lookup(champion_id) -> str | None` callable rather than loading the champion catalog itself.** The published runtime state only ever carries champion *ids* in `draft_snapshot`; resolving one to a display name needs `load_champion_catalog()` (a filesystem/network-adjacent operation this module must never perform, matching its "no filesystem access" contract), so that responsibility is deferred to whichever caller already has a loaded catalog (the eventual desktop app). No `name_lookup`, or one that returns `None` for an unrecognized id, both degrade to an id-bearing label rather than a guessed name — the same "never fabricate" discipline `champion_name_from_id()` itself already applies at the data layer, just repeated one layer up for the case where no catalog is available at all.
- **Malformed recommendation entries are silently skipped in `build_recommendation_cards()`, not rendered incompletely or raised on.** A missing required shared-schema field indicates a bug upstream in `recommend_draft()`, which already validates every entry it emits via `validate_recommendation()` before returning — this module's skip is a defensive second layer for a case that shouldn't occur in practice, not a normal/expected path, so it fails soft (dropping just the one bad entry) rather than crashing an otherwise-healthy poll's entire UI update.
- **`build_recommendation_cards()` copies `details.score_breakdown` through verbatim rather than exposing `details` alone and letting a future widget dig into it.** Pulling it out as its own top-level card field makes explicit, at the presentation-model boundary, that this value is inspectable-but-never-recomputed display data — reinforcing `UI_DESIGN.md`'s "no UI-side thresholds" rule at the one call site most tempted to violate it (a scored ranking is exactly the kind of value a UI author might otherwise be tempted to re-derive or re-sort by).
- **Demo fixtures (Stage 4) live under `demo/states/` as checked-in, version-controlled JSON, not generated in Python and not placed in `tests/fixtures/`.** They aren't test-only data — the eventual `--demo` mode (Stage 7) is meant to load and publish the exact same files a developer or reviewer can open and read directly, so `demo/` (a new top-level directory, sibling to `src/`/`tests/`/`reports/`) names that dual purpose honestly rather than hiding runtime-facing sample data inside the test tree. Not added to `.gitignore` (unlike `reports/runtime/` and `reports/captures/`) because these are authored, permanent content, not regenerable output.
- **`load_demo_states()` validates every fixture against the real `validate_state_shape()`/`validate_recommendation()` functions rather than a parallel demo-specific check.** Same "one definition of valid" discipline `state_reader.py` already established for `validate_state_shape()` — a demo fixture that wouldn't actually be accepted by the real pipeline is a bug in the fixture, and reusing the real validators is what catches that at test time instead of at demo runtime.
- **`src/ui/widgets/` has exactly one widget class per `build_presentation()` section, and each widget's only public surface is its `update_*()` method plus small read-only properties for tests to inspect.** No widget ever reaches back into `src/ui/presentation.py`, `state_reader.py`, or any recommendation/League module itself — data flows one direction, in through `update_*()`, matching the "keep UI code separate from recommendation logic, League API logic, and filesystem parsing" rule given for this whole session. `RecommendationListWidget` is the one widget that rebuilds its child widgets from scratch on every `update_cards()` call (rather than updating existing labels in place) because, unlike the other three sections, its *shape* changes between polls (a different number of recommendations), not just its text.
- **`src/ui/app.py`'s `build_application()`/`build_main_window()` are split out as separate, directly-testable factory functions from the blocking `main()`**, mirroring `src/draft/cli.py`'s own `main()`-is-thin, injectable-functions-underneath convention. `QApplication` permits only one live instance per process, so `build_application()` reuses `QApplication.instance()` when one already exists rather than letting a second construction raise — this is what lets every Qt-backed test module in this stage safely call it at import time without needing to coordinate a single shared fixture across files.
- **Every Qt test sets `QT_QPA_PLATFORM=offscreen` via `os.environ.setdefault(...)` as the first line of the test file, before any `PySide6` import, rather than depending on the shell environment.** This project's tests must stay runnable with a single `python -m tests.<module>` invocation and no special setup (per this session's "no interactive window during tests" rule) — baking the platform override into the test file itself, rather than into a shared test runner or `CHECKPOINT.md`-documented shell convention, is what guarantees that stays true even if a future contributor runs one test file in isolation.
- **`LiveStateSource` (Stage 6) hands the raw `StateReadResult` across threads via a Qt `Signal(object)`, rather than pre-translating it into a presentation dict before `emit()`.** Doing the translation inside the background-thread callback would mean `build_presentation()` (and any future translation logic) runs on the polling thread instead of the GUI thread — harmless today since that function is pure and cheap, but it's the wrong thread for the *concept* of "decide what to render," and it would make `LiveStateSource` responsible for a decision (`StateReadResult` → renderable shape) that already has an owner (`MainWindow.update_from_state_result()`). Emitting the raw, already-fully-built `StateReadResult` keeps `LiveStateSource` doing exactly one job — safe cross-thread delivery — and nothing else.
- **`MainWindow.update_from_state_result()`, not `presentation.py`, owns the mapping from the four reader-level `StateReadResult` statuses to a status header.** `presentation.py`'s documented contract is specifically "takes a `DraftRuntimeService`-shaped app-state dict" (Stage 3) — teaching it about `state_reader.py`'s separate five-status vocabulary would blur that boundary and couple two modules that currently don't need to know about each other at all (`presentation.py` still has zero imports from `state_reader.py`). Putting the bridge in `main_window.py` instead keeps it exactly where the other app_state→widget bridge (`update_from_app_state()`) already lives.
- **`file_missing` renders as `severity: "low"`, while `invalid_json`/`invalid_state_shape`/`read_error` all render as `severity: "high"`.** A missing state file is the ordinary, expected condition before anything has ever published one (or right after a fresh install) — not evidence of a problem. The other three all indicate something actually went wrong (a corrupt write, a shape mismatch, an OS-level read failure) and should visually read as more urgent than "nothing's happened yet," matching this project's general severity-as-impact (not confidence-as-correctness) axis established in `src/recommendations/schema.py`.
- **`--demo` mode (Stage 7) publishes fixtures through the real `publish_state()` into a separate demo-only path (`DEFAULT_DEMO_STATE_PATH`, sibling to but never overlapping `draft_state.json`), rather than feeding `MainWindow` directly or reusing the real runtime path.** Two reasons: (1) it keeps demo mode flowing through the *exact* same `LiveStateSource`/`StateWatcher`/`update_from_state_result()` pipeline real data uses — nothing in this project's UI stack has a demo-only code path a bug could hide in — and (2) a shared path would mean running `--demo` while `src/draft/cli.py --watch` happens to be running concurrently could silently stomp real runtime data (or vice versa) with no warning either way.
- **`DemoStatePublisher` only starts its repeating `QTimer` when given more than one state.** A `--demo-state NAME` single-fixture session that still ran a timer would either do nothing useful (rewriting byte-identical content every interval — `StateWatcher`'s content-based change detection would just discard the repeats anyway) or waste a background timer tick for zero benefit; skipping timer construction entirely for the one-fixture case is the simpler, equally-correct choice.
- **`build_arg_parser()`/`resolve_state_path()`/`build_demo_publisher()` are pulled out as separate, directly-testable functions rather than inlined into `main()`**, extending the same "thin `main()`, tested functions underneath" split `src/draft/cli.py` established and Stage 5's `build_application()`/`build_main_window()` already continued — `main()` itself stays permanently untested-by-design (it blocks on `app.exec()`), so every piece of real decision-making (which path to watch, whether demo mode applies, which fixtures to load) has to live in a function `main()` merely calls, or it would have no test coverage at all.
- **`src/ui/dev_launcher.py` (Stage 8) was kept, not skipped, because both processes it launches already existed as independent, already-tested entry points** (`src/draft/cli.py --watch`, `src/ui/app.py`) — this module adds no new League/recommendation/UI logic of its own, only `subprocess` orchestration around two things a developer could already run by hand in two terminals. That kept it small enough to fit the session's "skip if disproportionately complex" allowance comfortably on the "build it" side rather than needing to be skipped.
- **`dev_launcher.py`'s forwarded-argument syntax requires a literal `--` separator before args meant for `src.ui.app`** (e.g. `python -m src.ui.dev_launcher -- --demo`), rather than letting flag-like tokens pass through un-marked. Confirmed by hand that `argparse.REMAINDER` does not reliably capture a leading flag-like token immediately after this launcher's own `--interval` option — only tokens after an explicit `--` are captured cleanly — so the `--` requirement isn't a style preference, it's what actually works with `argparse.REMAINDER`. `resolve_app_args()` strips that leading `--` back out before building the forwarded command, so `src.ui.app` itself never sees it.
- **Stage 9 explicitly declined to wire `load_champion_catalog()` into `src/ui/app.py`'s `main()`, even though it would close the last champion-name-resolution gap flagged repeatedly through this session.** `load_champion_catalog()` calls `fetch_latest_version()` unconditionally on every invocation with no offline/cached-only path — wiring it into `main()` would make every desktop app launch, including fully-offline `--demo` mode, silently require network access to resolve one cosmetic label. This is a real product tradeoff (offline usability vs. one resolved name), not an oversight, and it's called out explicitly rather than silently deferred so a future session doesn't wire it in reflexively without re-considering the offline cost. A future fix would need to make the load optional/best-effort/non-blocking (e.g. only attempted once, failures silently degrading to the existing `"Champion ID N"` fallback) rather than a plain unconditional call.
- **The recommendation list's `QScrollArea` wraps only `self.recommendations`, not the whole central widget.** The status header and diagnostics sections are always the most important context (current state, errors, warnings) and must stay visible regardless of how long the recommendation list gets — scrolling the entire window would let a long list push critical status information off-screen, which is exactly the kind of thing `UI_DESIGN.md`'s "every unavailability/error marker must stay visible" principle argues against, one layer up from data into layout.
